# Ограничение памяти AGY

Geminka использует `agy acp --stdio`: асинхронный JSON-RPC, отдельный `sessionId`
для каждого диалога и один сервер для совместимых файловых прав. Два пользователя
одной группы делят процесс AGY, но не историю, модель или личность MCP-инструментов.
Владелец, разные группы и фоновые запросы без MCP разделены песочницами; один
процесс на все права означал бы потерю этой защиты. HTTP-порт не открывается.

`AGY_MAX_LIVE_SESSIONS=2` ограничивает число активных ACP-диалогов одного
клиента Geminka. Если лимит занят активными ответами, следующий новый диалог ждёт.
Свободная наименее недавно использованная сессия освобождается при необходимости.

`AGY_SESSION_IDLE_SECONDS=300` закрывает простаивающую ACP-сессию через 5 минут;
проверка выполняется каждые 30 секунд. Активные и ожидающие своей очереди запросы
на этой сессии не прерываются. После закрытия последней сессии сервер этого профиля
и его дочерние процессы завершаются вместе. Закрытие одного диалога не завершает
остальные диалоги общего сервера. MCP подключается отдельно для каждой сессии:
requester_id и брокер группы не передаются через общее окружение AGY.

В AGY ACP 1.5.8 `session/close` оставляет дочерние MCP-процессы в кеше сервера.
Поэтому ограничено не только число активных диалогов, но и число подключений за
жизнь сервера (тот же `AGY_MAX_LIVE_SESSIONS`). При исчерпании бюджета новый диалог
ждёт завершения активных запросов этого профиля; оставшиеся свободные диалоги
паркуются, сервер и MCP завершаются, затем точные ID загружаются по необходимости.
Обычные повторные сообщения в уже подключённом диалоге бюджет не расходуют.
Это предотвращает накопление MCP при потоке новых участников группы.

Перед освобождением сессии сохраняется её точный `sessionId`, инструкции
и курсор группового контекста. Следующее обращение в том же режиме вызывает
`session/load` с этим ID, а не с последним чужим диалогом. События старой истории,
которые ACP отдаёт при загрузке, не передаются в Telegram. Файлы истории и SQLite
не удаляются. Метаданные возобновления живут в памяти процесса бота: перезапуск
самого бота не обещает сохранения этой таблицы маршрутизации.

Одноразовые фоновые генерации всех клиентов сериализованы общим семафором:
максимум один такой запрос одновременно. Его сессия и освободившийся ACP-сервер
закрываются сразу после завершения.
Это ограничивает процессы, не размер каждого отдельного контекстного окна и не
общую память WSL; файловый кеш и другие приложения учитываются отдельно.

При обрыве/тайм-ауте отправленный запрос не повторяется автоматически: MCP уже
мог выполнить действие. Если отмена зависшего запроса не подтверждается за 5 секунд,
сервер закрывается; другие активные диалоги того же профиля также получат ошибку.
Старый stream-json-клиент оставлен как базовый класс и для регрессионных тестов;
диалоги, сканер стикеров, наблюдатель, ежедневные задачи и саммари используют ACP.

Изменения лимитов в `.env` требуют перезапуска целевого экземпляра.
