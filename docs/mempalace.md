# Долговременная память MemPalace

`./run.sh` устанавливает закреплённый Git-коммит MemPalace через `uv sync`.
Прямой Python API MemPalace включён в обработку личных Telegram-сообщений.
Модель ответа по-прежнему работает через OMP/Antigravity; MemPalace хранит
и извлекает данные, но не является провайдером генерации.

## Хранение и обработка

- `memory/users/<telegram-user-id>/`: отдельное хранилище MemPalace/Chroma на пользователя.
- `dialogue`: оригинальный текст/caption, роли, Telegram message/chat ID, время UTC,
  тип медиа; длинные тексты разбиваются на фрагменты без потери оригинала.
- `facts`: автоматические факты, события, цели, предпочтения, наблюдения настроения,
  гипотезы; каждая автоматическая запись содержит ID сообщения-основания и даты источников.
- `portrait`: актуальный портрет; `portrait_history`: предыдущие редакции.
- `control`: состояние обработки, счётчики и маркер переноса старой памяти.
- `agent_persona`, `agent_portrait`: отдельные тематические записи и портрет Коломбины;
  `agent_sources`, `agent_history`: исходные описания и версии. Они не используются
  при автоматическом составлении портрета человека. Портрет агента (до 4000 символов)
  передаётся отдельным полем `agent_persona` в пределах общего бюджета контекста.
- `shared/`: общий обезличенный контекст проекта из `memories/SHARED_CONTEXT.md`;
  при старте файл синхронизируется по SHA-256, старые фрагменты удаляются, а найденные
  по запросу куски доступны каждому пользователю как `shared_context`.

Перед ответом сохраняется сообщение и выполняется векторный поиск по его содержанию.
В контекст передаются до восьми результатов и портрет, суммарно до 18 000 символов JSON.
На продолжающейся Antigravity-сессии память также прикладывается к последнему сообщению:
шлюз в этом режиме не пересылает обновления системного промпта.

Извлечение воспоминаний идёт фоном через отдельный запрос к выбранной пользователем
модели, без пользовательского conversation ID. Это дополнительные обращения к провайдеру
и расход его квоты. Обработка сериализована, исходные сообщения сохраняются до анализа.
Временные ошибки провайдера повторяются до трёх попыток. Невалидный JSON или
исчерпание попыток оставляет события pending; повтор происходит
при следующем сообщении или запуске приложения. При остановке даётся 20 секунд на завершение.

Первый портрет создаётся после первого успешного анализа. Затем он пересматривается
после каждых 50 обработанных сообщений пользователя. Для пересмотра передаются предыдущий
портрет, последние 50 сообщений (превью до 700 символов каждого) и недавние извлечённые
воспоминания с общим бюджетом. Полные тексты остаются в векторном архиве.
Настроение временное; предположения о характере помечаются как оценки модели.
Модель не может знать невысказанные мысли. Проверка ссылок подтверждает наличие источника,
но не доказывает правильность интерпретации — портрет стоит периодически просматривать.

Фото/голос/видео не транскрибируются этим модулем: сохраняются caption и тип медиа.
Тексты вложений, чужие цитаты и служебные инструкции из обработчика не записываются
как собственные слова пользователя. Личная память используется только в личном чате;
групповые запросы получают отдельный короткий контекст и не видят личный palace.

## Старые данные и запуск

При первом запуске выполняется идемпотентный перенос оставшихся сообщений и фактов
из `data/state.db`. `memories/USER.md`, `MEMORY.md`, `facts.json` переносятся только
в palace владельца. Источники не удаляются. Старые записи помечены непроверенными;
прежний составной промпт не выдаётся за чистую речь пользователя и не идёт в автоанализ.
Сообщения, ранее удалённые ограничением SQLite в 200 записей, восстановить нельзя.

SQLite остаётся для настроек, conversation ID и короткого окна диалога. Все новые
долговременные факты, архив и портрет хранятся в MemPalace; `/remember` пишет туда же.
Прежний эвристический adaptive-портрет в личном чате больше не формируется и не
подмешивается в контекст. Эмоциональное состояние самой Геминки остаётся отдельным.
Отдельный исходный checkout MemPalace не нужен: зависимость закреплена на
`5a2abffe575b9706be376dde383396555c1121ff` в `pyproject.toml` и `uv.lock`.

Используется многоязычная локальная ONNX-модель `embeddinggemma`. При первом обращении
скачиваются веса с Hugging Face. Веса кэшируются, последующие embeddings локальные.
При анализе архивных сообщений соответствующие данные отправляются текущему LLM-провайдеру.
Менять `MEMPALACE_EMBEDDING_MODEL` у существующего palace без переиндексации нельзя.
Каталог `memory/` исключён из Git и Docker build context, в Compose подключён как volume.

```bash
uv sync --frozen
uv run python -m scripts.check_palace_memory
uv run python -m scripts.check_palace_memory --gateway
./run.sh
```

Проверка использует временный каталог и синтетические данные, не запускает Telegram polling.
`--gateway` выполняет реальные модельные запросы через настроенный OMP.

## Команды

- `/memory` — сохранённые факты и портрет (просмотр ограничен 500 записями).
- `/portrait` — актуальная редакция портрета.
- `/recall вопрос` — векторный поиск с датами и источниками.
- `/remember текст` — явная запись факта.
- `/forget confirm` — удалить palace-данные пользователя и короткий контекст, сбросить
  conversation ID. Старые исходники/бэкапы и серверные сессии провайдера не удаляются;
  маркер предотвращает повторный импорт из SQLite. Другие пользователи не затрагиваются.

Перед обновлением делайте резервную копию `memory/` при остановленном боте.
Для отката к старой реализации сохранён исходный SQLite. Новые MemPalace-записи в него
не зеркалируются, поэтому при откате необходимо сохранить и `memory/`.
